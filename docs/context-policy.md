# 是否需要自动配置，以及上下文如何设置

本页是插件的设计判断，查证日期 2026-11-18。公开工具的在线文档与 `main` 源码会变化，下面的策略不能直接当成旧版本的默认值。

## 需求判断

**值得自动化的是有出处的模型元数据补全。** 用户经由第三方网关添加新模型、模型部署名与标准 ID 不同、一次导入多个模型时，逐项查上下文、输出、识图与推理参数既繁琐又容易出错。填错容量也会影响压缩时机。

这对 DSH 有具体价值。当前核对的 DSH 0.2.2-rc.3 中，pi-ai 已为内置目录模型提供默认参数；它自己的模型发现也能读取部分渠道能力，插件不需要替代这些功能。缺口主要是自定义渠道：普通 `/models` 未必声明能力，未知模型会使用适配器的容量回退值（文档默认上下文 1,000,000、输出 128,000），这些数值不证明部署真实支持；发现结果结构还没有推理等级。插件能减少这些场景的手工配置与错误假设。

其他工具也维护模型目录：Codex 使用模型元数据与缓存，OpenCode 使用 models.dev、provider 集成与用户覆盖，Aider 使用 LiteLLM 元数据。这能证明问题普遍存在，但不能证明本插件有广泛市场需求。其定位适合是补足 DSH 自定义渠道的轻量工具，后续可观察用户是否减少手工修正、哪些字段经常填错，再决定是否继续扩展。

自动化的边界：

- 用户已有值优先；自动升级需要匹配的插件回执，仅凭外形与默认模板一致不够。
- 渠道 API 明确字段优先；原厂、镜像和第三方目录都应保留来源，并标明渠道未验证。
- 不知道就留空，不能把模型名猜测或通用回退值描述成检测结果。
- 不以请求成功来证明模型容量或推理参数生效；网关可能忽略参数。容量不通过大量计费请求探测。
- 推理能力、可接受的等级、实际发送的协议参数是不同问题；只有等级表也不保证任意网关的协议兼容。

## 四种上下文相关数值

| 数值 | 含义 | 由谁决定 |
|---|---|---|
| 模型/部署容量 | API 实际允许的上下文、输入与输出限制 | 服务端部署、账号档位及模型版本 |
| Agent 工作预算 | 实际愿意维持多少上下文，可能小于容量 | 用户或 Agent 策略 |
| 压缩阈值 | 何时整理历史、生成摘要 | Agent 策略 |
| 输出上限及预留 | 本次最多生成多少，以及为生成和其他开销留多少空间 | 模型约束与请求策略 |

配置窗口为 1M 并不会立刻发送 1M 内容。软件填写原生上限，仍然可以按更小的预算压缩。软件显示较小数字，也可能是在表示工作预算、扣除输出后的可用输入，而非宣称模型原生能力更小。

需要先核对字段语义：有的 API 上下文包含输入和输出，有的目录分别给输入限制。不能普遍将 `max_input_tokens` 当成完整上下文，也不能总是再加一次输出。当前插件把渠道含义不清的输入/输出字段降为参考值；第三方目录的一致也只是补全证据，不能替代服务端契约。

## 长上下文与质量

“越长越容易受干扰、检索和长程推理精度可能下降”有依据；“每多一个 token 就一定变差”或“所有模型超过某个长度都会掉智”没有统一依据。[Anthropic 的上下文工程文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)明确称其为逐步的性能变化，而非统一断崖，同时提醒过度压缩会丢掉后来才显得关键的细节。

因此不存在通用的“所有模型设成 32K/64K”标准。长资料理解可能需要保留原文；长时间编码任务则常受益于按需读文件、裁掉冗余工具输出、保存决策和待办、摘要旧历史，并保留可重新检索的原始记录。应比较实际任务正确率、延迟、费用、摘要遗漏与溢出频率，再调整工作预算。

## 在 DSH 中的建议

当前 DSH 0.2.2-rc.3 随包 `dsh-compaction-basic` 文档给出的默认触发公式为：

```text
T = floor(min(W × thresholdRatio, W − O − headroomTokens))
默认 thresholdRatio = 0.8
默认 headroomTokens = 65536
```

`W` 为适配器声明的窗口，`O` 为实际请求输出预留；最近历史默认按 `W − O` 的 16% 保留原文。这些是该版本随包默认值，用户的实际配置或 `modelPolicies` 可以覆盖，并非本次读取了用户的私有配置。

例如 `W=262144`、`O=32768` 时，默认 `T=163840`，已经早于窗口上限。把容量再随意改小会继续压低阈值，甚至使 `W − O − B` 非正。小窗口模型尤其应单独调小 headroom；单调 `thresholdRatio` 不能解决输出与 headroom 已占满窗口的问题。

建议插件填写有证据的模型/渠道容量，不自动改 DSH 的压缩策略。若用户希望更早整理上下文，调整独立的 `thresholdRatio`、`headroomTokens` 或精确路由的 `modelPolicies`。模型页手填较小窗口作为临时运行限制可以工作，但应记住它混合了容量与策略，之后来源更新也不该擅自抬高它。

## 名称与别名

自动匹配只放宽大小写、渠道前缀与常见分隔符差异；完整日期、短日期、版本数字和 `:free` 等变体保留。不同快照或免费档可能有不同容量，不能靠去后缀提升命中率。已明确的 canonical ID 和用户显式映射比模糊名称更可靠。

别名只重定向元数据查询，不修改实际请求 ID，也不改变渠道鉴权。浮动别名应优先使用目录中的显式记录，不自动指向“最新快照”。现有无日期模型线的同系推断仅保留推理等级且要求同一厂商已披露快照一致，仍属于推断；不共享容量，不对变体推断。

后续若实际用户遇到同名部署在不同渠道指向不同模型，可增加渠道作用域别名；没有足够案例前不引入正则、递归映射或自动去除 `thinking`、`latest` 等语义后缀，以免难以审计。
